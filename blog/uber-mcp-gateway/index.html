Uber's MCP Gateway, explained

October 3, 2026 · ai · infrastructure

Verdict: Uber put a single gateway in front of every tool its AI agents can touch — 800+ MCP servers, 5,000+ tools — and in doing so solved the three problems that kill agent projects at scale: discovery, auth sprawl, and context bloat. You don't need Uber's scale to steal the ideas: discover tools incrementally instead of preloading them, trim tool responses before they reach the model, and let the agent write code instead of making fifty round trips.

What MCP is, in one paragraph

The Model Context Protocol is a standard plug for AI agents — USB-C for tools. Before it, every agent needed a custom integration for every data source: one handshake for the database, another for Slack, another for the internal API. MCP defines one discoverable way for a model to list tools and call them, so agent builders spend their time on the agent instead of the socket. (Anthropic introduced it in late 2024; it now lives under the Agentic AI Foundation.)

Why Uber built a gateway

When agents took off inside Uber, every team started exposing tools its own way. Internal APIs weren't agent-accessible at all, and each SaaS tool had its own auth and setup dance — so building an agent meant weeks of plumbing before you wrote a single prompt. The fix was a centralized MCP Gateway: one place where tools get registered, discovered, authorized, and called. It now fronts 800+ MCP servers and 5,000+ tools, and every agent-to-tool call passes through it.

The architecture: two planes

Control Plane — the registry and the crawler. The MCP Registry is where servers are looked up and where teams register their own. Next to it runs the AutoCrawler: it scans Uber's IDL (interface definition language) registry and generates MCP tool definitions from service metadata automatically. Exposing a Thrift, gRPC, or HTTP endpoint as an MCP server becomes a configuration change — zero rewrites to the underlying service. Internal services get lighter scrutiny and auto-generation; third-party servers get rigorous review and are blocked by default in production.

Data Plane — the proxy. The Proxy Gateway translates between MCP and whatever the backend speaks (HTTP, gRPC, TChannel), handling authentication, authorization, rate limiting, telemetry, and audit logging in one place instead of in every team's hand-rolled proxy. It also fronts SaaS tools like Google, Slack, and Jira: the gateway manages hosting and token exchange, so engineers get one common way to install and call any MCP.

Three ideas worth stealing

Uber's exact numbers won't transfer to your setup, but the methodology does. These three are the payload:

1. Omni MCP — discover tools incrementally. The naive approach loads every tool definition into the model's context up front. At Uber's scale that was reportedly 50–70K tokens of schema per session — and because every turn re-sends history, the tax was repaid on every single turn. Omni MCP flips it: a single entry-point MCP that can discover and invoke any other MCP in the gateway on demand. Tool search becomes the primary interface; schemas are pulled in only for the task at hand. Overhead stops growing with the size of your tool library.

2. Response Projection — trim payloads before they hit context. Even with discovery solved, fat tool responses eat context. Uber's CLI pattern resolves and invokes the tool at the moment it's needed, and the response is projected down so it barely touches the context window. Same principle as discovery: never pay for what the model doesn't need.

3. Code Mode — batch tool calls into scripts. Under vanilla MCP, each tool action is its own round trip. Code Mode (via the aifx CLI) lets the model write a small script that runs the whole sequence in a subprocess, with only the final summary returned to context. Uber ships roughly 25 pre-packaged "code-mode skills" for its most-used tools so the efficient path is the default, not something engineers opt into. Reported result across these optimizations: around 40% fleet-wide token savings.

The one-liner: Treat your tool layer like infrastructure, not an afterthought — one gateway for auth, discovery, and observability, plus incremental discovery, trimmed responses, and code-mode batching to keep the context window for actual reasoning.
