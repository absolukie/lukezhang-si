Are Unit Tests Dead?

engineering · ai · 10 min

An engineer ran 444 agent coding runs, banned his agents from writing tests, and found the tests were not doing anything. The twist: this does not mean you need fewer tests. It means you need different ones.

Here is the tweet that started all of this. Kun Chen (@kunchenguid) builds the DeepSWE eval: 111 real-world coding tasks, run 444 times through Claude Sonnet 5.5. One arm of the experiment told the agent it was allowed to write tests. The other arm banned it from writing any tests at all.

Then he compared the two arms. Tap to zoom the gaps.

The success rate barely moved. The bill did. Banning test-writing changed task success by +0.9 points (too small to be real) while cutting time 6% and spend 9% (both real).

Source: kunchenguid's post, Oct 2026. 444 runs on Claude Sonnet 5.5 across 111 real-world tasks. Of the tests written in the allowed arm, 65% were unit tests and 35% integration tests, and neither group helped.

His conclusion, blunt: tell your agents to stop writing tests by themselves. And do not ask them to do TDD either, he says he has data that it hurts.

But wait. Read the fine print before you delete your test folder. He banned the agent writing its own tests. He did not test human-written tests, and the eval had almost no end-to-end tests (17 of them versus 3,000+ unit and integration tests). So the honest headline is narrower: tests written by the same agent that wrote the code did not help.

The mirror problem

This is the core of the whole debate, and it is one picture. The agent reads your request and forms an interpretation of what you want. Then it writes the code from that interpretation. Then it writes the tests from that same interpretation. Both the code and the tests are downstream of the same brain reading.

Why self-written tests cannot catch misreading

Toggle between self-check and independent check.

Self-check: 1,200 tests, all green. The bug ships anyway, because the tests checked the agent's reading of your request, not your request.

This is the "independent X-ray machine" argument from Zhouwei: what AI needs is requirement-level verification where the questions come from a different teacher, one who only looked at the curriculum and never saw the student's notes. Quentin Haenn calls the failure mode "AI slop": code that is syntactically valid but business-false. The test suite, written by the same agent, never thinks to cross-reference the two files.

The verdict

The middle position won this debate, and it was not close. Tests are more important in the agent era, not less. But they have to be a different kind of test: an independent check on the author's work, not a second draft of the author's thoughts.

The pyramid, flipped

The old pyramid said: lots of unit tests, a few e2e tests. Agents changed the cost curve, so the pyramid flips.

End-to-end first, because agents write and self-heal e2e tests cheaply. Unit tests last, as golden fixtures derived from real debugging sessions, not as fine-grained guesses the agent rarely gets wrong anyway.

After: the "inverted pyramid" position from the debate, and Kun Chen's own conclusion: unit tests written by the implementer sit "closer to source code than independent product proof." Requirement-anchored tests, written from the request before the agent starts, beat post-hoc tests every time.

DHH said the quiet part out loud in a post I saved last month: there is no future where you manually review every line of agent code. What replaces it is adversarial agent review, automated testing, and maybe a spot check. This whole post is the receipt for that sentence. The tests are not dead. The self-graded tests are.

Tests as an independent check on an author you don't fully trust will be the most valuable code you own.
