Evals, explained

October 3, 2026 · ai · testing

Verdict: An eval is a standardized test for an AI model — a fixed set of tasks, run the same way every time, with a fixed way of scoring, so you get a number instead of a vibe. They are how the industry decides whether a new model is actually better. They are also easy to game, easy to misread, and blind to the things that matter most in real use.

The idea in one paragraph

Think SATs for AI. You take a model, give it the same questions you gave every other model, grade the answers the same way, and compare the scores. Without that, "this model feels smarter" is just a feeling — and feelings don't survive contact with a harder task. Evals turn "better" into something you can measure, track over time, and argue about with data.

Anatomy of an eval

Every eval has three parts:

1. The tasks. A dataset of prompts — math problems, coding challenges, questions with known answers, or multi-step jobs like "fix this bug in this repo." The tasks are fixed and public (or held back) so everyone runs the same test.

2. The harness. The machinery that feeds each task to the model exactly the same way — same system prompt, same tool access, same time limits. This matters more than people think: change the harness and the scores change, even with the same model.

3. The scorer. How answers get graded. Sometimes it's exact ("did the code pass the hidden tests?"), sometimes a rubric, and increasingly it's another AI model acting as judge — which works, but means your measurement now depends on the judge's own quirks.

The famous ones

A few names you'll keep seeing: MMLU (general knowledge across 57 subjects), HumanEval (write small Python functions), SWE-bench (fix real GitHub issues in real repos — much harder, much more realistic), GSM8K (grade-school math, where models famously learned to show their work). The newer and more interesting breed is agent evals: the model gets a terminal, a browser, or a codebase and has to complete a whole job, not just answer a question. That's the closest thing to measuring real usefulness.

Why they matter to you

If you've ever compared two models on the same prompt and picked a winner, you've run an eval — just an informal one. The Model Bench comparisons (same prompts, graded side by side) are a hand-rolled eval. Formalizing it only means: write the prompts down, fix the grading rule, and re-run it every time something changes. Then "did the new version get worse?" stops being a debate and starts being a number.

Where evals lie

Three honest caveats:

Teaching to the test. If a model trained on the eval's questions (called contamination), its score measures memorization, not ability. This happens more than anyone admits.

Narrow tests, messy world. An eval measures what it measures. A model can ace coding benchmarks and still write code you'd never merge — because the eval didn't test readability, taste, or knowing when not to write code at all.

Goodhart's law. Once a score becomes the target, it stops being a good measure. Labs optimize for the leaderboard, and the leaderboard drifts away from what users actually feel.

How to read an eval claim

When someone says "our model scores 92% on X," ask three questions: was the harness the same as everyone else's (or did they tune it?), could the model have seen the test during training?, and what does the test not cover that I care about? A number without those answers is marketing. A number with them is useful.
