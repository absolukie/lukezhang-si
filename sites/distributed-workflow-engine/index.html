How it maps

GitHub Actions → durable execution
workflow file→ definition (the DAG's shape)
workflow run→ run, with real wall-clock timestamps — no virtual clock
job→ parallel task — jobs fan out like the ETL transforms
step→ sequential node inside its job's DAG
conclusion→ terminal state: success / failure / cancelled / skipped
run_attempt→ retry count, shown in the run header

Live shows history, not a live tail — GitHub's API reports completed steps; in-progress steps update when you hit ⟳ refresh. Workers, heartbeats, timers, signals and the chaos panel only exist in the Sandbox.

Timers & signals

Two modes. Sandbox is a deterministic in-browser simulation — but the event log is real: every durable fact on this page (runs, steps, queue, timers, signals, worker liveness, stats) is derived by folding that log ( and see); only volatile live-process detail — a task's remaining-seconds countdown, heartbeat ages — isn't. Deliberately so: partial progress is always discarded on recovery, exactly like a real worker restart. Task durations, flaky steps and virtual time are simulated; the recovery semantics — heartbeats, leases, backoff, idempotent replay, saga compensation — are implemented, not animated. Live shows your actual GitHub Actions runs instead: real timestamps, durations and conclusions fetched from api.github.com (cached aggressively; 60 calls/hour without a token).
