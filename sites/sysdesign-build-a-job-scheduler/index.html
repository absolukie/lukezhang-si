Build a Job Scheduler

Delayed jobs, cron jobs, and the machinery that runs them while you sleep.

"Design a distributed job scheduler. I want one-shot delayed jobs and cron jobs, retries when things fail, and a way to deal with jobs that never succeed. How do you make sure every job runs on time, even when machines die?"

On this page: takeaway · requirements · capacity math · architecture · deep dives · API + data model · trade-offs · failure modes · what I'd actually build · interview tips · live scheduler simulator

🎯 The takeaway, first

A distributed scheduler is three boring pieces bolted together: a durable table of (run_at, job) rows, workers that lease due jobs with heartbeats instead of just grabbing them, and retries with exponential backoff ending in a dead-letter queue. "Distributed cron" is just "cron with a database and a lease."

The sentence that carries the interview: "At-least-once delivery with idempotent jobs, leases so a dead worker's job gets picked up, and backoff plus a DLQ so one poison job can't wedge the whole system." Everything else — cron parsing, dashboards, timezones — is UI on top of that core.

🚫 Misconception, busted

"Cron on one server is fine — I'll scale later." A single box running cron has three silent killers: no retries (a 3am deploy kills the 3:05am job and nobody notices until Monday), no failover (the box dies, the jobs die with it), and the thundering herd (fifty 0 * * * * jobs all fire at the top of the hour and OOM the box together). The fix isn't "a bigger cron box" — it's making scheduled time a row in a database that any worker can claim. That one move buys you retries, failover, and observability in a single stroke.

01Requirements

Functional

  • Schedule a one-shot job: run this payload once, at time T (or in N seconds).
  • Schedule a recurring job: cron expression, timezone-aware.
  • At-least-once execution: a job runs even if the worker that picked it up dies mid-run.
  • Retries with exponential backoff + jitter; after N failures, park it in a dead-letter queue for humans.
  • Cancel / pause / trigger-now controls.

Non-functional

  • No single point of failure: any scheduler node can die without losing jobs.
  • Second-level scheduling precision (nobody needs millisecond cron).
  • No double-execution beyond the lease window — and jobs must be idempotent anyway.
  • Scale target: schedule 10k jobs/sec, run 100k concurrent delayed jobs without the poller melting.

02Back-of-envelope math

Analogy first: the scheduler is a restaurant kitchen's ticket rail. The math tells you how long the rail needs to be and how many cooks you need before tickets start falling on the floor.

QuantityAssumptionResult
Job rows1M delayed jobs alive at once, 1 KB payload each~1 GB — fits in Postgres comfortably; the index on run_at is the hot path
Due-job pollPoller grabs jobs with run_at <= now every 500ms, batch of 500Sustains 1,000 jobs/sec dispatch; poll query must be an index-only scan or it melts
Workers needed100 jobs/sec arriving, avg job takes 2sLittle's law: 100 × 2 = 200 concurrent slots — size the fleet from this, not vibes
Lease heartbeats200 workers × heartbeat every 10s20 writes/sec — trivial; heartbeats are cheap, lost leases are expensive
Retry storm1% of 10k jobs fail, naive immediate retry100 extra jobs/sec hammering an already-sick downstream — this is why backoff exists

Takeaway after the math: the system is dominated by two numbers — the due-job index scan and Little's-law worker sizing. Get those right and the rest is plumbing.

Go deeper: why SKIP LOCKED is the hero of this diagram

Multiple pollers (or poller threads) racing to claim due jobs need a way to split work without a distributed lock. SELECT ... FOR UPDATE SKIP LOCKED lets each poller grab a batch of unlocked rows and skip rows another poller already locked — no coordination, no waiting, near-perfect sharding of the due set. It's the closest thing databases have to a built-in work queue, and it's why "just Postgres" is a legitimate answer for surprisingly large schedulers.

04Component deep-dives

Leasing: how a dead worker doesn't eat your job

A worker doesn't take a job — it leases it, like renting a car with the keys due back. It stamps lease_owner + lease_expires on the row and heartbeats to extend. If the worker dies, the lease expires and the poller re-queues the job. No lease, no safety.

Retries, backoff, and the dead-letter queue

A failed job doesn't retry instantly — that just DDoSes whatever is already sick. Each attempt waits 2^attempt seconds (plus random jitter so a thousand failures don't all retry at the same instant), and after the cap it's parked in the DLQ with its error history attached.

sequenceDiagram
    participant W as Worker
    participant R as Retry planner
    participant D as Dead-letter queue
    W->>R: job #7 failed (attempt 1)
    R->>R: wait 2s + jitter, requeue
    W->>R: job #7 failed (attempt 2)
    R->>R: wait 4s + jitter, requeue
    W->>R: job #7 failed (attempt 5, max)
    R->>D: park with error history, alert human

05API + data model

API

  { name, run_at | cron, timezone,
    payload, max_attempts, backoff_base }
  -> { job_id, next_run_at }

GET /jobs/{id}          # status + attempt history
DELETE /jobs/{id}       # cancel a scheduled job
POST /jobs/{id}/trigger # run now, out of schedule
GET /dlq                # poison jobs awaiting humans
POST /dlq/{id}/requeue  # forgive and retry

Data model: one table does the work

iduuid pk
run_atindexed — the hot path
statusscheduled · pending · running · done · dead
attempt / max_attemptsretry counting
lease_owner / lease_expiresnullable
cron / timezonenull for one-shots
payloadjsonb

Cron jobs are just a template row; the leader materializes the next run_at after each firing. DLQ can be a status, not a separate table — but alerting queries it like one.

07Failure modes

  • Split-brain cron leaders — two leaders materialize the same cron tick twice. Mitigation: fencing via the advisory lock + unique constraint on (cron_id, scheduled_for) so the double-insert fails loudly.
  • Clock skew — a worker 30s in the future heartbeats "successfully" while its lease logic misfires. Mitigation: NTP everywhere, and compare timestamps only on the DB server's clock.
  • Poison jobs — a job that fails deterministically (bad payload, deleted downstream table) retrying forever. Mitigation: attempt cap + DLQ + alert. The simulator below shows this live.
  • Thundering herd — 5,000 jobs scheduled for midnight all become due in the same poll. Mitigation: jitter the materialized run_at by seconds, rate-limit the poller batch.
  • Long jobs vs. short leases — a 10-minute job with a 30s lease gets re-queued mid-run and executes twice. Mitigation: heartbeat from the execution thread, and lease duration ≥ p99 job duration.

08What I'd actually build

  • Postgres as the job store — SELECT ... FOR UPDATE SKIP LOCKED for claiming, advisory lock for the single cron leader. One database, zero new infra.
  • Poller every 500ms, batch 500; workers lease 60s with 10s heartbeats from the execution thread.
  • Backoff: min(2^attempt, 300)s + jitter(0–30%), cap 8 attempts, then DLQ + PagerDuty.
  • Every job payload carries an idempotency key; handlers must tolerate re-execution — documented, tested with a chaos "kill -9 the worker" drill.
  • Cron materialization writes (cron_id, scheduled_for) with a unique constraint — double-leader inserts die loudly instead of double-firing.
  • If the team already runs Kubernetes: Temporal instead of hand-rolling — durable execution is this exact system, productized.

09Interview tips

  • Say "at-least-once plus idempotent jobs" in the first two minutes — it defuses the exactly-once trap before the interviewer sets it.
  • Draw the lease explicitly: lease_owner, lease_expires columns on the whiteboard. Interviewers remember the drawing.
  • When they ask "how do workers find due jobs," answer SKIP LOCKED — it's the shibboleth for "has built this."
  • Ask the scoping question: "Second-level precision or millisecond? And are jobs idempotent today, or is that part of the design?"
  • Close with the DLQ: juniors forget it, seniors lead with it. Poison jobs are inevitable; the design question is what happens after attempt N.

Go deeper: why jitter the backoff?

Without jitter, a thousand jobs that all failed at 12:00:00 retry at 12:00:02, then 12:00:06 — synchronized stampedes that re-overwhelm the recovering downstream. Adding ±30% random jitter smears retries across time. It's the difference between a retry storm and a gentle rain. The simulator uses pure powers of two so you can see the doubling clearly; production adds the jitter.
