Design a distributed cache

Everyone's favorite interview topic — and everyone's favorite production footgun. A cache doesn't make your system fast. It makes your system fast on average, and the average hides the stampedes.

🎯 The takeaway, first

Cache-aside is the default; write-through when you can't afford stale reads. But the real design isn't the happy path — it's the invalidation story and the thundering-herd plan. Think of the cache like a whiteboard next to the filing cabinet: reading the whiteboard is fast, but someone has to erase it when the files change, and if the whiteboard gets wiped, a hundred people rushing the cabinet at once will jam the door. If you can't say what happens when the cache is cold, you don't have a cache design — you have a hope.

🚫 Misconception, busted

"Adding a cache always makes things faster." A cold cache makes p99 worse than no cache (every request pays cache-lookup plus DB). A hot key can melt a single shard while the rest sit idle. And a stale-cache bug serves wrong data at lightning speed — confidently. The cache is a liability you manage, not a turbo button you bolt on.

Requirements

Say these out loud before drawing a single box.

Functional

  • GET / SET / DELETE with TTL and LRU eviction
  • Scale out: add nodes without rehashing everything
  • Key namespacing (svc:entity:id)
  • Stats: hit rate, evictions, per-key hotness

Non-functional

  • p99 < 5ms, 1M+ ops/s
  • 99.99% availability — survive a node loss without avalanche
  • Hit rate ≥ 95% at steady state
  • Bounded staleness: define it, don't discover it
  • No single key may take down a shard

Go deeper: why does adding a node only move 1/N of keys?

Consistent hashing places both nodes and keys on a ring; each key belongs to the first node clockwise from it. Adding a node only steals the key ranges immediately counter-clockwise of its positions. With plain modulo hashing (key % N), changing N reshuffles nearly every key — a full cache flush in disguise. Virtual nodes (each physical node claims ~1000 ring positions) smooth out the distribution so no node gets a lumpy share. Draw the ring in the interview; it's the expected picture.

Architecture

The centerpiece: the client library owns the ring.

The client library hashes the key and talks directly to the owning shard — no proxy hop. Each shard has a replica for failover. On a miss, the app (not the cache) loads from the DB — that's what makes it cache-aside. The singleflight map sits in the app layer: 100 concurrent GETs for the same missing key collapse into one DB query, and 99 waiters share the result.

Component deep-dives

Cache-aside read + write (the default)

        A->>D: SELECT ... (singleflight dedups)

Write-through (when stale is not an option)

    C->>D: write-through (sync)

API + data model

GET    /cache/{key}            → 200 {value} | 404
SET    /cache/{key} {value, ttl_s}
DELETE /cache/{key}
EXPIRE /cache/{key} {ttl_s}
key format:  {service}:{entity}:{id}      e.g.  web:user:42
value:       { v: 3, data: {...} }         -- versioned! readers ignore v < expected
metadata:    TTL = 300s + rand(±30s)       -- jittered, always
Go deeper: why version the value?

Rolling deploys mean old and new code share the cache. A version field lets new code ignore (and overwrite) values written by old code instead of deserializing garbage. It's also your escape hatch for a bad serialization deploy: bump the version, old entries become invisible, no flush needed.

Failure modes

Thundering herd: hot key expires under loadSingleflight + jittered TTLs + probabilistic early refresh (one request refreshes at 90% TTL)
Hot key melts one shardDetect via per-key counters; replicate the key to N shards; small local L1 in the app
Cold restart (fleet deploy wipes cache)Rolling restarts; warm from replicas; never flush the whole ring at once
Cache penetration: attackers request keys that never existBloom filter of known keys in front; short negative caching ("null" with 10s TTL)
Node dies mid-writeReplica promotion; client retries on the replica; 1/N of keys briefly miss — acceptable

What I'd actually build

Opinionated. Steal this for the interview.

Stack: Redis Cluster, client-side consistent hashing in the app, singleflight in the request path, TTL = 300s ± jitter always. Cache-aside with delete-on-write; write-through only for balances/inventory. Redis pub/sub invalidation channel so every app instance drops its local L1 on writes. Versioned values. Dashboards: hit rate, eviction rate, per-shard hotness, singleflight collapses/sec. Load-test the cold-start path quarterly — that's the one that pages you at 3am.

Interview tips

  • Draw the ring. Consistent hashing with virtual nodes is the expected picture — draw it before they ask.
  • Say "thundering herd" early. Then defuse it with singleflight. It's the highest-value 60 seconds in this interview.
  • TTL jitter is a free point. One sentence — "jitter every TTL so nothing expires in a cliff" — signals production experience.
  • Name what you won't cache. "Money-shaped data goes write-through or bypasses the cache" shows judgment.
  • Close with the cold start. Ask them: "want me to walk through a full fleet restart?" — it reframes you as the operator, not the theorist.
