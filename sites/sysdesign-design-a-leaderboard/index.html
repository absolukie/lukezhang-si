Design a real-time leaderboard

"A mobile game with 1 million daily players needs a live global leaderboard. Scores update constantly, ranks must feel instant, and it has to survive tournament spikes without melting."

⚡ The takeaway first

A leaderboard is a sorted set, not a SQL table. Keep one ordered structure per game where every score update re-sorts in O(log n), read the top 100 straight off the top, and answer "what's my rank?" with a single rank lookup. Then shard by game — each game's leaderboard lives on its own shard, so nothing global ever needs a lock.

📋 Requirements

Functional

  • Submit a score for a player in a game; keep the player's best score.
  • Read top-N (N ≤ 100) for a game, and "players around me" (rank ± 10).
  • Rank query: "what is my rank right now?"
  • Seasonal resets (weekly tournaments start fresh).

Non-functional

  • Writes: ~2k score updates/sec sustained, 20k/sec tournament spikes.
  • Reads: 20k top-N reads/sec — reads dominate writes ~10:1.
  • Freshness: a new high score is visible within ~1 second.
  • Scale: 1M players per popular game, thousands of games.
🚫 Common misconception

"Just store scores in Postgres and ORDER BY score DESC LIMIT 100." That sorts a million rows on every page view — or leans on an index that must be rewritten on every single score update, turning each write into index churn. A sorted set (Redis ZADD/ZREVRANK) keeps the order incrementally: updates cost O(log n), top-N reads are O(log n + N), and rank is a single lookup. That's the entire data structure decision, and it's the one interviewers are waiting for.

🧮 Back-of-the-envelope math

AssumptionValue

Read rate200k reads/sec across games (top-N + rank)
ZADD cost at 1M membersO(log 1M) ≈ 20 comparisons ≈ sub-millisecond

One Redis shard handles ~100k ops/sec comfortably. So a single game needs 2–3 shards at peak, and 1,000 quiet games share shards by hashing game id. Memory for 1,000 games × 100k players avg ≈ 6.4 GB. This is a small system that looks big — the interview trap is over-architecting it.

Go deeper: why not just cache the top 100?

You could recompute top-100 every second and serve from cache — and many games do exactly this for the displayed board. But "what's my rank?" for player #483,201 still needs the full ordering, and rank lookups are the long tail of reads. The sorted set answers both from the same structure, so keep it as source of truth and cache only the rendered top-N page.

🏗️ Architecture

The centerpiece: shard by game, sorted set per shard, thin API in front.

Think of it like a tournament bracket board per game: each game gets its own whiteboard (shard) with names already in order. Updating a score is erasing one name and rewriting it in the right slot — you never re-sort the whole board. The router just makes sure everyone playing game 42 walks to the same whiteboard.

🔍 Component deep-dives

Score submit — best-score-wins, one round trip

sequenceDiagram
    participant C as Game client
    participant S as Leaderboard service
    participant R as Redis shard
    C->>S: POST /games/42/scores {player, score:9500}
    S->>R: ZADD gt game:42 9500 player:7
    Note over R: GT flag: only update if greater.
O(log n), atomic.
    R->>R: ZREVRANK game:42 player:7
    R-->>S: rank 1,203
    S-->>C: 200 {rank: 1203, top: [...]}

The GT flag matters: "keep my best score" becomes atomic — no read-modify-write race between two concurrent submissions from the same player.

Rank query + "around me" — two lookups, no scans

sequenceDiagram
    participant C as Client
    participant S as Leaderboard service
    participant R as Redis shard
    C->>S: GET /games/42/rank?player=7
    S->>R: ZREVRANK game:42 player:7
    R-->>S: 1202 (0-indexed)
    S->>R: ZREVRANGE game:42 1192 1212 WITHSCORES
    R-->>S: 21 entries around the player
    S-->>C: {rank: 1203, neighbors: [...]}

Two O(log n) operations. The client renders "you are #1,203, here are the 10 above and below you" — which is the view players actually care about, not the global top 100.

🔌 API + data model

API

POST /v1/games/{gameId}/scores
  { "playerId": "p7", "score": 9500 }        → { "rank": 1203, "isBest": true }

GET  /v1/games/{gameId}/top?n=100           → [{playerId, score, rank}...]
GET  /v1/games/{gameId}/rank/{playerId}     → { rank, score, neighbors:[...] }
POST /v1/games/{gameId}/seasons             → snapshot + reset (weekly)

Data model

  • Key: lb:{gameId}:{season} → Redis sorted set, member = playerId, score = best score. Ties: member suffix or score micro-offset keeps ordering deterministic.
  • Shard map: hash(gameId) → shard — a game never spans shards, so no cross-shard queries exist.
  • Archive: on season reset, ZRANGE the final board to S3 as JSON/Parquet; serve "last season's winners" from there.

🔥 Failure modes

  • Tournament thundering herd — 20× write spike at season start. Mitigation: client-side score batching (submit at most 1/sec), gateway rate limits per player, shards scale by game popularity.
  • Hot shard — one viral game saturates its Redis. Mitigation: read replicas for top-N/rank reads; split the game's ZSET across 2 shards by player-hash only if truly needed (rank then needs a merge — avoid unless forced).
  • Clock/ordering disputes — "I submitted first!" Mitigation: server timestamp on write; tie-break documented in the rules.
  • Season reset race — scores landing mid-snapshot. Mitigation: freeze writes for ~1s during snapshot (return 503 with Retry-After), or snapshot-then-replay.

🛠️ What I'd actually build

Redis Cluster (or Upstash/ElastiCache Serverless if I want zero ops) as the entire stateful layer — sorted sets are the product. Stateless Go or Node API behind a gateway, sharded by hash(gameId) with a static shard map in config. Score events also published to Kafka for anti-cheat analytics offline. Season snapshots to S3. Client SDK batches submissions and polls rank at most every 5s. Total custom code: a few hundred lines. The interview answer is "Redis sorted sets + shard by game" — everything else is operational detail.

🎤 Interview tips

  • Lead with the data structure: "sorted set per game, sharded by game id" in the first 60 seconds.
  • When they ask about scale, do the 64 MB per million players math out loud — it shows the problem fits in RAM and deflates the urge to over-design.
  • Mention the GT flag / best-score atomicity — it's a small detail that signals real Redis knowledge.
  • Always bring up cheating unprompted; leaderboard interviews are secretly about trust.
  • If they ask for global cross-game rank ("best player across all games"), push back: that's a different product — aggregate asynchronously, never on the read path.
Go deeper: percentile ranks and "top 1%"

ZCOUNT gives "how many players are below X" in O(log n) — so "top 1%" badges are one extra lookup: rank / ZCARD. No new infrastructure, just arithmetic on values you already have.
