Design a Rate Limiter

The bouncer at the door of every API.

"Design a rate limiter. I need to cap users at N requests per time window across a fleet of API servers. Token bucket or sliding window — which, and how do you make it work distributed?"

On this page: takeaway · requirements · capacity math · architecture · deep dives · API + data model · trade-offs · failure modes · what I'd actually build · interview tips · live firing range

🎯 The takeaway, first

A rate limiter is a bouncer with a clicker counter. Every request asks "am I allowed?", the limiter checks a per-key counter against the rule, and answers yes or 429 Too Many Requests — ideally in under a millisecond, on the request's hot path. The two classic algorithms differ in one question: token bucket asks "do I have a token saved up?" (bursts allowed, smooths average rate), sliding window asks "how many did you send in the last N seconds?" (stricter, no bursts).

The interview sentence: "Token bucket when bursts are legitimate, sliding window when the limit is a hard ceiling; either way, keep the counters in Redis with a Lua script so the check-and-decrement is atomic."

🚫 Misconception, busted

"Rate limiting is just if count > limit: reject with a counter that resets every minute." That's fixed window limiting, and it has a famous hole: a user can send limit requests at 12:00:59 and limit more at 12:01:01 — double the intended rate across the boundary, completely "legally." Sliding window closes the hole by always looking back a full window from now, and token bucket closes it differently by making bursts spend saved-up tokens. If your design has a counter that resets on a clock tick, an interviewer will drive a truck through the boundary.

01Requirements

Functional

  • Limit by key: user ID, API key, or IP — configurable rules per endpoint.
  • Return 429 with Retry-After when over the limit; include X-RateLimit-Remaining headers on success.
  • Rules like "100/min, 1000/hour" simultaneously (tiered limits).
  • Per-key configuration that updates without a deploy.

Non-functional

  • Sub-millisecond check — it runs before anything else on every request.
  • Works across N API servers: counters must be shared, not per-process.
  • Must not become the outage: fail open (allow traffic) if the limiter store is down.
  • Handle 100k decisions/sec with headroom.

02Back-of-envelope math

Analogy first: the limiter is a toll booth. The math tells you how many lanes (Redis ops) you need so the booth never becomes the traffic jam.

Takeaway after the math: the limiter's cost is one Redis round-trip per request and a few hundred MB of state. The expensive mistake isn't the algorithm — it's failing closed and turning a Redis blip into a full outage.

03Architecture

Picture the toll booth again: every car (request) stops, the attendant (Lua script) checks the ledger (Redis) and either waves it through or holds up the red paddle — all in one atomic motion so two booths can't both wave through the last token.

Go deeper: why a Lua script and not GET + DECR?

Two API servers checking the same key at the same microsecond could both read tokens=1, both decrement, and both allow — the classic check-then-act race. A Lua script runs atomically inside Redis: refill calculation, comparison, and decrement happen as one indivisible step. No locks, no races, one round trip. Every production rate limiter does the decision in a single atomic script; if your design has the app server doing read-then-write, that's the bug the interviewer is hunting for.

04Component deep-dives

Token bucket: the bouncer with a token jar

Each key has a jar holding up to capacity tokens, refilling at rate per second. A request takes one token; empty jar means 429. A full jar lets a burst of capacity requests through instantly — that's the feature: it smooths the average while tolerating bursts.

sequenceDiagram
    participant G as Gateway
    participant R as Redis (Lua)
    G->>R: EVAL check(key, now)
    R->>R: refill = (now - last) * rate
    R->>R: tokens = min(capacity, tokens + refill)
    alt tokens >= 1
        R->>R: tokens -= 1
        R->>G: ALLOW, remaining=tokens
    else tokens < 1
        R->>G: DENY 429, retry_after
    end

Sliding window: the strict accountant

Keep the timestamps of recent requests (a sorted set in Redis). On each request, drop timestamps older than window, count what's left: under the limit → allow and record now; at the limit → 429. No bursts, no boundary exploits — the window always looks back a full N seconds from this instant.

sequenceDiagram
    participant G as Gateway
    participant R as Redis (Lua)
    G->>R: EVAL check(key, now)
    R->>R: remove timestamps older than now - window
    R->>R: count = remaining timestamps
    alt count < limit
        R->>R: add now to the log
        R->>G: ALLOW, remaining = limit - count - 1
    else count >= limit
        R->>G: DENY 429, retry_after
    end

07Failure modes

  • Failing closed — Redis blips, limiter rejects everything, you DDoS yourself. Mitigation: fail open with a metric screaming about it. A limiter that causes outages is worse than no limiter.
  • Hot keys — one API key doing 50k rps hammers a single Redis key (and single hash slot). Mitigation: shard hot keys, or do local probabilistic pre-limiting per server.
  • Clock skew on refill — bucket refill math uses timestamps; skewed clocks across app servers distort rates. Mitigation: compute refill from Redis server time inside the Lua script.
  • Retry storms from 429s — clients hammering through 429s multiply load. Mitigation: Retry-After headers + exponential backoff on the client; the 429 must teach, not just punish.
  • Key cardinality explosion — limiting per IP with IPv6 = unbounded keys. Mitigation: cap keyspace, aggregate (/64 subnets), TTL aggressively.

08What I'd actually build

  • Token bucket as the default (bursts are legitimate for user traffic), sliding window on auth/login/billing endpoints where the ceiling is contractual.
  • Redis Cluster, one Lua script per decision (atomic refill + check + decrement), keys rl:{rule}:{key} with TTL = 2× window.
  • Refill math from Redis server time inside the script — immune to app-server clock skew.
  • Rules in a config service, hot-reloaded; tiered rules evaluated in a single script pass.
  • Fail open on Redis errors, with a dedicated alarm. The limiter is a bouncer, not a load-bearing wall.
  • Client contract: honor Retry-After, exponential backoff on 429s — enforced in our own SDKs, documented for everyone else.

09Interview tips

  • Open by naming the fixed-window boundary hole before they ask — it signals you've thought about adversarial users.
  • Say "Lua script, atomic" when they ask how N servers share counters. It's the whole distributed answer in three words.
  • Draw both algorithms' state per key (2 numbers vs. timestamp list) — the memory math lands harder as a picture.
  • Volunteer fail-open unprompted. Interviewers ask "what if Redis dies?" to check exactly this.
  • Ask the scoping question: "Is the limit protecting us from abuse, or enforcing a billing tier? That picks the algorithm."

Go deeper: where does the limiter live — gateway or service?

At the API gateway / edge for coarse limits (per IP, per API key) — it sheds load before it touches your fleet. Finer limits (per user per endpoint, billing tiers) live as middleware in the service, where the key and the rule context exist. Big systems run both: the edge stops the flood, the service enforces the contract. And the counters? Always shared (Redis) — per-process counters across a fleet are just N independent limiters pretending to be one.
